Browser Autofill Detection Research for a Local Clarity Lab

This report summarizes what a local test page can observe when form fields are filled by browser autofill, copy/paste, script-driven fills, password managers, and browser automation. It is intended to guide the next HTML lab page that embeds a Microsoft Clarity tag.

Prepared: July 22, 2026 Target: local browser test page Clarity project id: pending Theme: light

Best current browser signal

Chrome has introduced a dedicated autofill event as an origin trial starting in Chrome 147. It fires before the browser fills the form and exposes planned autofill values plus a refill function. It is promising, but it is not a stable cross-browser baseline yet.

Best practical stable signal

CSS :autofill and :-webkit-autofill can identify fields currently styled as browser-autofilled. This is useful, but limited. The state disappears when the user edits the field, and support/behavior varies.

Main limitation

Page JavaScript cannot perfectly prove intent. It can distinguish ordinary paste and simple script fills well, but it cannot always distinguish browser autofill from sophisticated automation or extension-based password managers.

Executive Finding

The local page should not rely on a single event. It should build a timeline and classify each value change from several signals: autofill where available, CSS autofill state, beforeinput, input, change, paste, drop, keyboard/pointer context, event.isTrusted, navigator.webdriver, value-property interception, mutation observers, and periodic value snapshots.

Recommended framing: label each detected change as a candidate with evidence, not as a definitive truth. For example: browser-autofill-likely, paste-observed, script-fill-observed, webdriver-or-automation-suspected, and unknown-value-change.

Observed Signals

Signal What it tells us How strong Failure modes
autofill event Direct signal that the browser is about to autofill a form. Chrome's origin-trial event includes an autofillValues array and a refill hook for dynamic forms. Strong Chrome origin trial only as of this report; not a stable cross-browser API.
:autofill / :-webkit-autofill The element currently matches the browser autofill pseudo-class. Can be sampled with element.matches() and observed through a CSS animationstart hook. Strong State can be lost after editing; support is not uniform; does not detect paste or script fills.
paste event The user initiated paste through browser UI. This is the cleanest differentiator for normal copy/paste. Strong Synthetic paste events can be dispatched but are untrusted; extensions may bypass ordinary event flow.
InputEvent.inputType Identifies edit categories such as insertText, insertFromPaste, insertFromDrop, undo, delete, and composition changes. Medium Not all input changes provide useful inputType; autofill historically looks generic or silent.
event.isTrusted Separates many browser/user-agent generated events from events sent with dispatchEvent(). Medium Trusted does not always mean human; untrusted is a strong synthetic-event clue.
Value setter interception A local wrapper around input value and checked setters can catch page scripts that assign input.value or input.checked. Medium Can miss native browser autofill, low-level automation, assignments before the wrapper runs, or code that uses native setters directly.
Polling/snapshots Detects silent value changes by comparing value length/hash snapshots across animation frames, load, focus, visibility changes, and submit. Medium Detects that a value changed, but not why.
navigator.webdriver Indicates when the browser exposes that it is under WebDriver control. Weak Useful when true; not proof when false. Automation can sometimes suppress or avoid this signal.
Event timing and clustering Browser autofill often changes several related fields in a tight cluster with no preceding keystrokes or paste event. Manual typing has key/input cadence. Paste has a paste marker. Weak High-fidelity automation can mimic timing. Users can also use unusual workflows.

Distinguishing Autofill, Paste, and Automation

Fill source Expected evidence Classifier label
Browser autofill Dedicated autofill event if available; CSS :autofill match; multiple related fields change together; no paste event; little or no keydown cadence. browser-autofill-likely
Copy/paste paste event, usually InputEvent.inputType === "insertFromPaste", field focused, and value change follows immediately. paste-observed
Drag/drop text drop event and often InputEvent.inputType === "insertFromDrop". drop-observed
Simple script or bot fill Value setter wrapper fires; any emitted input/change events are isTrusted === false; no CSS autofill state; no human input lead-in. script-fill-observed
Browser automation using keystrokes navigator.webdriver may be true; keydown/input sequence may look like typing, but timing can be too regular and no prior pointer context is needed. automation-suspected
Password manager or extension fill May look like script fill, may dispatch synthetic events, may fill on focus, and may not match :autofill. Treat separately from browser-native autofill. manager-or-extension-fill-suspected
Unknown silent value change Snapshot sees value changed, but no event, no setter hook, no CSS autofill state, and no automation flag. unknown-value-change

Clarity Implications

The local Clarity source in this repo records input interactions from input events and includes an event trust bit. It also has clipboard tracking for cut, copy, and paste. That makes the proposed lab valuable because it can show cases where page JavaScript sees a signal that Clarity will likely record, and cases where a browser autofill changes values silently.

  • Local source note: packages/clarity-js/src/interaction/input.ts binds input and stores evt.isTrusted.
  • Local source note: packages/clarity-js/src/interaction/clipboard.ts binds cut, copy, and paste.
  • Local source note: packages/clarity-js/src/interaction/click.ts records click trust and has diagnostic source logic for untrusted clicks.
Privacy constraint: Microsoft Clarity documentation says input box content, numbers, and email addresses are classified as sensitive and masked content is not uploaded. The lab should still use fake autofill profiles and mask the on-page event log by default, because copied values displayed outside input controls can become ordinary page text.

Recommended Local Lab Design

  1. Serve the page from http://localhost, not directly through file://. This more closely matches production browser behavior and avoids surprises with third-party scripts, storage, and origin-bound browser features.
  2. Insert the Clarity tag early, but install local instrumentation before it when testing network and event capture ordering. The lab can accept the Clarity project id from a query string or a visible setup field until a permanent id is provided.
  3. Include several real autofill-friendly forms with explicit autocomplete tokens: name, email, tel, street-address, address-line1, address-level2, postal-code, username, current-password, new-password, and one-time-code.
  4. Log captured events in a fixed event stream: focus, blur, keydown, keyup, beforeinput, input, change, paste, copy, cut, drop, animationstart, autofill, submit, and visibilitychange.
  5. Record event metadata: timestamp, target id/name/type/autocomplete, active element, value length, stable per-session value hash, inputType, data length, isTrusted, keyboard key/code, modifier keys, pointer state, navigator.webdriver, user activation state, and current CSS autofill match.
  6. Add test controls for controlled non-browser fills: assign .value only; assign and dispatch synthetic input/change; call setRangeText(); trigger HTMLElement.click(); and run batched multi-field script fills.
  7. Monkey-patch fetch, XMLHttpRequest, and navigator.sendBeacon before loading Clarity so the page can show outgoing Clarity request URLs, method, body length, and timestamps without dumping payload bodies.
  8. Send Clarity custom events and tags for the page's classifier output, for example clarity("event", "fill_browser_autofill_likely") and clarity("set", "last_fill_candidate", "paste-observed").

Implementation Sketch

CSS autofill instrumentation

const autofillSelectors = [":autofill", ":-webkit-autofill"];

function matchesAutofill(element) {
  return autofillSelectors.some((selector) => {
    try {
      return element.matches(selector);
    } catch {
      return false;
    }
  });
}

document.addEventListener("animationstart", (event) => {
  if (event.animationName === "autofill-start") {
    logFillSignal(event.target, "css-autofill-animation", event);
  }
}, true);

Value setter instrumentation

function wrapInputValueSetter() {
  const descriptor = Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, "value");
  Object.defineProperty(HTMLInputElement.prototype, "value", {
    configurable: true,
    get: descriptor.get,
    set(value) {
      logFillSignal(this, "value-setter", { valueLength: String(value).length });
      return descriptor.set.call(this, value);
    }
  });
}

Classification model

function classify(change) {
  if (change.autofillEvent || change.cssAutofill) return "browser-autofill-likely";
  if (change.pasteEvent || change.inputType === "insertFromPaste") return "paste-observed";
  if (change.dropEvent || change.inputType === "insertFromDrop") return "drop-observed";
  if (change.valueSetter || change.syntheticEvent) return "script-fill-observed";
  if (navigator.webdriver || change.machineLikeCadence) return "automation-suspected";
  return "unknown-value-change";
}

Research Notes

  • :autofill is explicitly defined as matching an input element whose value has been autofilled by the browser, but MDN marks it as limited availability.
  • The generic input and change events describe that a value changed or was committed; they do not identify the value source. Chrome's autofill event article calls out that limitation directly.
  • The paste event is a strong differentiator because it is fired when the user initiates paste through browser UI. Pair it with inputType === "insertFromPaste" when available.
  • event.isTrusted is useful for catching synthetic events from dispatchEvent(), but trusted events can still be generated by the user agent for programmatic browser operations.
  • navigator.webdriver is useful when true. It should not be used as a negative proof that no automation exists.

Open Questions for the Lab

  • Which browsers should be included in the first test pass: Chrome stable, Chrome Canary with origin trial, Edge, Safari, Firefox, or a narrower set?
  • Should the on-page log show actual values, value hashes, or both behind a toggle? The safest default is lengths and hashes only.
  • Should the page load the public Clarity snippet from Microsoft, the local repo build, or support both modes?
  • Should the report and lab include a Playwright/WebDriver script to generate automation baselines?
